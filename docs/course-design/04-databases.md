## Module rules (decided here)

| Topic | Rule |
| :--- | :--- |
| Lab database | The learner's own free Supabase project, named `gpis-rebuild-dev`. Never a project with real data. Made in unit 4.1 |
| Connection | `.env` (never committed) holds `LAB_DATABASE_URL` = the project's **session pooler** connection string. `.env.example` gains the name only |
| The marker | The first migration creates `public.academy_lab (purpose text not null)` with one row `'ruftech-academy lab'`. Without it every `sql` step reports `needs` |
| Migrations | Every schema change is a new file in `supabase/migrations/` named `<timestamp>_<what>.sql`, applied with the Supabase CLI (`npx supabase db push`). An applied migration is never edited: a mistake is corrected by a new one (GPIS security rule 4). No change is made in the dashboard's table editor |
| Reset | `npx supabase db reset --linked` rebuilds the lab database from the migrations and `supabase/seed.sql`. Lessons say plainly: this deletes everything in the lab database, and that is why it is a lab |
| Tools | `psql` (`sudo apt install postgresql-client`) and the Supabase SQL editor. Lessons use `psql "$LAB_DATABASE_URL"` |
| Identity columns | `bigint generated by default as identity` (not `always`): the checks insert their own rows with fixed ids |
| Check rows | `sql` steps add their own rows in `setup:` with ids from 900001 and names that start `ZZ `, inside the checker's transaction; everything is rolled back. They never rely on the learner's own rows, and never count rows without a filter on those ids |
| Results | Counts as `::int`, dates and numerics as `::text`, always `order by` (guide 10.4) |
| Names | Tables and columns below are a **contract**: `lab.md` prints the names; the learner chooses types and constraints inside the rules given |
| RLS from the start | Every `create table` is followed by `alter table … enable row level security` in the same migration, from 4.1, with no policy (deny by default). Policies come in 4.4. The owner connection used in labs is not limited by RLS |

## GPIS rules used in this module

| Rule | Text to use |
| :--- | :--- |
| GPIS security rule 3 | Every table has RLS enabled with explicit policies. A new table ships with RLS on and zero policies before it ships with any policy. Deny by default |
| GPIS security rule 4 | Every schema change is a migration file in `supabase/migrations/`; never a change through the dashboard |
| GPIS security rule 2 | Role comes from `app_metadata`, never `user_metadata`: `user_metadata` is writable by the user's own browser |
| **D-19** | Class membership is a separate record of a period: student, class, academic year, start date, nullable end date, and the terms it covers. A student may have several in one year |
| **D-20** | Students move between classes only at term boundaries, so a term always belongs to exactly one class |
| **D-21** | Every score references the membership record it was earned under, resolved once at write time and never recalculated. Nothing resolves a class at read time |
| **D-22** | The database prevents overlapping memberships, not application code. "A constraint cannot be forgotten by a shortcut." |
| **D-23** | Student status and membership status are separate. A withdrawal ends the membership and sets the status. A return opens a new membership; the gap is the absence. Alumni is a status, never a class |
| **D-27** | Maximum marks are stored on each score record, not assumed from a constant; enforced by database CHECK constraints against the stored maxima. Class category decides the score ranges |
| **D-162 / D-171 / D-10** | As in module 2: parts and maxima; exam maximum 100 or 140; zero, blank and `ABS` differ; no total unless every part is a number |
| **D-45** | Class matching ignores case, spacing and punctuation, and is never fuzzy ("JHS 3", "jhs3", "J.H.S 3" are one class) |
| **D-02 / D-03 / Q-07 / D-04** | As in module 2: competition ranking, one class only, JHS 3 not ranked, missing subjects add nothing, open membership **and** active |
| GPIS AGENTS.md | "This project has already lost a test database to an agent-run process." (Used in 4.6 as the reason backups are practised.) |

## Unit 4.1 — Tables, keys and migrations

### Front matter

| Field | Value |
| :--- | :--- |
| id / project | `m4-u1` / `m4-p1` |
| title | Tables, keys and migrations |
| module / position | 4 / 1 |
| guidance | half |
| minutes | 900 |
| gpis_part | The first GPIS tables: students, classes, academic years, terms, as migrations that replay from empty |
| requires | `[wsl, node, git, supabase, lab-db]` |

### Outcomes

After this unit you can:

1. create a Supabase lab project and connect to it from the terminal without exposing its password;
2. design a table with the right types, a primary key, and NOT NULL, UNIQUE, CHECK and foreign-key constraints;
3. write `select`, `insert`, `update` and `delete` for one table;
4. change a schema only through migration files, and rebuild the database from them;
5. explain why the database, not the application, must refuse wrong data.

### Lesson (two parts)

| § | Section | Key ideas |
| :--- | :--- | :--- |
| A1 | What a relational database is | Tables, rows, columns; one fact in one place; SQL is a language for questions |
| A2 | The lab project | Create it; the connection string; `.env`; `psql`; the marker table and why the checker demands it |
| A3 | Types | `text`, `bigint`, `smallint`, `date`, `timestamptz`, `boolean`, `numeric`; choose the narrowest that tells the truth |
| A4 | Keys | Primary key; identity columns; a natural key (`admission_number`) is unique but not the primary key |
| A5 | Constraints | `not null`, `unique`, `check (…)`, `references`; what the error message looks like |
| B1 | Four statements | `select … where … order by`, `insert … returning`, `update … where`, `delete … where`; forgetting `where` |
| B2 | Generated columns | `canonical_key` computed from `name`; unique on it makes "Basic 3" and "basic-3" the same class (D-45) |
| B3 | Migrations | A numbered file per change; `supabase init`, `link`, `migration new`, `db push`; never edit an applied file |
| B4 | Replaying | `db reset --linked`; seed data in `supabase/seed.sql`; "works on my database" against "works from empty" |
| B5 | RLS on, no policy | Every new table: enable RLS at once. With no policy, nobody but the owner reads it (GPIS security rule 3) |
| B6 | In GPIS | `students` has no class column (D-19); every change is a migration (rule 4) |

- **Diagram (text):** four boxes — `academic_years` 1—many `terms`; `classes`; `students` — with no line from `students` to `classes`, and a note "the link arrives in 4.2".
- **Common mistakes**
  1. A rule kept only in the form's code → another screen or a script writes bad rows → a constraint.
  2. `update students set status = 'withdrawn'` without `where` → every student is withdrawn → write the `where` first.
  3. Editing an old migration to fix it → your database and a fresh one differ → a new migration.
  4. Creating a table in the dashboard "just to try" → it exists nowhere in the repository → migration file.
  5. `text` for a date → "31/02/2026" is accepted → `date`.

### Guided example — "A library catalogue" (first half in full)

A scratch Supabase project is **not** needed: the example uses the lab project and a schema
`example_library` that its last step drops.

6. Now add a generated column `title_key` (lower case, letters only) and make it unique; insert "Things Fall Apart" and "things fall apart!". *(task)*

## Unit 4.2 — Time in the database

### Front matter

| Field | Value |
| :--- | :--- |
| id / project | `m4-u2` / `m4-p2` |
| title | Time in the database |
| module / position | 4 / 2 |
| guidance | half |
| minutes | 960 |
| gpis_part | The temporal model: class membership as a dated record; overlaps refused by the database (D-19 to D-23) |
| requires | `[wsl, node, git, supabase, lab-db]` |

### Outcomes

After this unit you can:

1. model "was in this class from this day to that day" as rows, and query "who was where, when";
2. join tables with `join … on`, and say which rows a `left join` keeps;
3. make overlapping periods impossible with an exclusion constraint;
4. change several rows as one unit with a transaction, inside a database function;
5. explain why the constraint lives in the database and not in a form.

### Lesson (two parts)

| § | Section | Key ideas |
| :--- | :--- | :--- |
| A1 | A fact with a period | Start date, nullable end date; open = `ended_on is null`; never a "current" flag |
| A2 | Joins | `join`, `left join`, aliases; "students with their open membership", "students with none" |
| A3 | Asking about a date | `started_on <= d and (ended_on is null or ended_on >= d)`; ranges: `daterange(a, b, '[]')`, `@>`, `&&` |
| A4 | Two rows that must never both exist | `unique` compares equal values; periods need "overlaps": `exclude using gist (student_id with =, daterange(…) with &&)`; the `btree_gist` extension |
| A5 | Terms of a membership | `membership_terms`; unique (`student_id`, `term_id`) = one class per term (D-20); the composite foreign key that keeps `student_id` honest |
| B1 | Transactions | `begin`, `commit`, `rollback`; all or nothing; what a half-done move would look like |
| B2 | Functions | `create function … language plpgsql`; parameters; `raise exception`; a function body is one transaction |
| B3 | Moving a student | End the old row the day before the term; open the new row on the term's first day; move the term rows; refuse a date inside a term |
| B4 | Withdrawing | End the membership **and** set the status, together (D-23); the history stays |
| B5 | In GPIS | D-22: legacy had five code paths that wrote a class, one of which recorded nothing; "a constraint cannot be forgotten by a shortcut" |

- **Diagram (text):** a timeline for one student across a year: Term 1 in Basic 3 `[14 Sep … 10 Jan]`, Term 2–3 in Basic 4 `[11 Jan … open)`, with the term boundaries marked and one crossed-out overlapping bar.
- **Common mistakes**
  1. Checking for overlap in application code → two requests at the same moment both pass → an exclusion constraint.
  2. Ending the old membership on the same day the new one starts with inclusive ranges → they overlap by one day → the day before.
  3. Two separate statements for a move, no transaction → the first succeeds, the second fails, the student has no class → one function.

### Outcomes

After this unit you can:

1. split a wide record into two tables and say what each row means;
2. store the rule a value was judged by (its maximum) beside the value;
3. use `null` correctly: compare with `is null`, and predict what `sum` and `+` do with it;
4. write CHECK constraints that compare two columns of a row;
5. build a view that calculates a total only when it is allowed to exist.

### Lesson

| § | Section | Key ideas |
| :--- | :--- | :--- |
| 1 | "28" against "28 out of 30" | A stored value must carry what it needs to be read later (D-27); a constant in code changes, the old rows do not |
| 2 | One score, five parts | `scores` (who, which term, which subject) and `score_parts` (part, maximum, mark, absent); composite primary key |
| 3 | The anchor | (`membership_id`, `term_id`) → `membership_terms`: a score can exist only for a term its membership covers (D-21). The class of a score is a join, decided when it was written |
| 4 | `null` | "Unknown", not zero. `null = null` is not true; `is null`; `coalesce`; `sum` skips nulls; `a + null` is null |
| 5 | Three states of a part | Number; blank (`mark is null and not absent`); ABS (`absent`). A CHECK forbids "absent with a mark" (D-162) |
| 6 | Checks across columns | `check (mark >= 0 and mark <= max_mark)`; `check ((part = 'exam' and max_mark in (100, 140)) or (part <> 'exam' and max_mark = 15))` |
| 7 | Aggregates and `filter` | `count(*) filter (where …)`, `sum(mark) filter (where part <> 'exam')`, `group by`, `having` |
| 8 | A view for the total | `score_totals`: `case when` every part is a number `then` … `end`; `round(x, 2)`; `security_invoker` so RLS still applies |
| 9 | In GPIS | D-21: reprinting an old term shows the old class; D-10: blank prints blank; three layers: Zod, Server Action, CHECK |

- **Diagram (text):** `membership_terms` ← `scores` ← `score_parts`, with one example row in each, and an arrow from the score through its membership to "Basic 3", labelled "decided at write time".
- **Common mistakes**
  1. `coalesce(mark, 0)` in the total → a blank becomes a zero → no total unless complete.
  2. `where mark = null` → never true → `is null`.
  3. Maxima in a constant or a separate "settings" row → changing it rewrites history → store it on the row.
  4. A score that points to student and class separately → nothing proves the student was in that class then → point to the membership.
  5. A view without `security_invoker` → it reads as its owner and skips RLS → set it.

### Lesson (two parts)

| § | Section | Key ideas |
| :--- | :--- | :--- |
| A1 | Who is asking? | The browser talks to the database through an API with a key. Publishable key → role `anon` or `authenticated`. Secret key → skips RLS; never in `src/` (GPIS security rule 1) |
| A2 | Grants and RLS | Two gates: table privilege (`grant`) and row policy. RLS on + no policy = no rows |
| A3 | A policy | `create policy … on t for select to authenticated using (…)`; `with check` for new and changed rows; policies of one command are joined with OR |
| A4 | The JWT | A signed note the server gave the user; `auth.uid()`, `auth.jwt()`; `app_metadata` set only by the server, `user_metadata` writable by the user |
| A5 | `app_role()` | One small `stable` function reads `auth.jwt() -> 'app_metadata' ->> 'role'`; every policy calls it |
| B1 | Roles of this course | `admin`: everything in the school data. `assessment`: reads students, classes, memberships, years, terms, subjects; reads and writes scores. No role: nothing |
| B2 | Acting as someone in SQL | `begin; set local role authenticated; select set_config('request.jwt.claims', '{…}', true); … rollback;` |
| B3 | Negative tests | For each role and table: what must be refused. A select that returns no rows is a refusal; an insert raises an error |
| B4 | Functions and views | `security definer` runs as the owner and skips RLS: allowed only with a check of `app_role()` inside and a fixed `search_path`; revoke `execute` from `public` and `anon` |
| B5 | Finding holes | Queries on `pg_class.relrowsecurity`, `pg_policies`, `pg_proc.prosecdef`, `information_schema.role_routine_grants` |
| B6 | In GPIS | Rules 1–3; "deny by default"; CI searches migrations for a table without RLS |

- **Diagram (text):** request → API key → database role → table grant → row policy (reads `app_role()` from the JWT) → rows.
- **Common mistakes**
  1. Reading the role from `user_metadata` → a user edits it in the browser and becomes admin → `app_metadata`.
  2. A policy `using (true)` "for now" → the table is public → write the real rule or none.
  3. An update policy with `using` but no `with check` → a user changes a row into one they could not have inserted → both.
  4. Testing as the owner → everything works, because the owner skips RLS → `set local role`.
  5. A `security definer` function with no role check → a door round every policy → check inside, or make it `invoker`.

### Lesson

| § | Section | Key ideas |
| :--- | :--- | :--- |
| 1 | Building a query in layers | `with a as (…), b as (…) select …`; test each layer alone |
| 2 | Grouping | `group by`, `count`, `sum`, `having`; every selected column is grouped or aggregated |
| 3 | Left joins and missing rows | A student with no score still appears, with a total of 0 from "nothing added" (Q-07), not dropped by an inner join |
| 4 | Window functions | `rank() over (order by total desc)`: 1, 1, 3. `dense_rank`: 1, 1, 2. `row_number`: 1, 2, 3. `partition by` |
| 5 | Who counts | Membership covers the term **and** `students.status = 'active'` (D-04): both conditions, in one place: `class_roll` |
| 6 | One class at a time | The function takes a class; nothing ranks across classes (D-03); a `jhs3` class returns no ranking |
| 7 | Table functions | `returns table (…) language sql stable`; `security invoker` (the default) so RLS applies; `grant execute … to authenticated` |
| 8 | Plans and indexes | `explain analyze`; `Seq Scan` against `Index Scan`; an index on what you filter and join by; indexes cost writes |
| 9 | In GPIS | The report card's position comes from one ranking function; the on-roll count uses the same roster as the ranking |

- **Diagram (text):** the layers of `class_ranking`: roll → subject totals per student → sum per student → `rank()`.
- **Common mistakes**
  1. `dense_rank()` → 1, 1, 2 → D-02 names it as wrong.
  2. Inner join from students to scores → a student with no scores has no position → left join.
  3. Filtering only `status = 'active'` → an active student of another class is ranked here → membership too.
  4. Ranking inside the page with JavaScript **and** in SQL → two answers that can differ → one function.
  5. Adding an index for every column → slower writes, no faster reads → index what the plan shows is scanned.

### Outcomes

After this unit you can:

1. take a logical backup with `pg_dump` and restore it, whole or one table;
2. measure two numbers for a system: how much data a failure can lose, and how long recovery takes;
3. explain why a replica copies a wrong `delete` as faithfully as a right one;
4. practise a restore before it is needed, and write down the steps that worked;
5. keep a backup file out of Git and away from people who must not read it.

### Lesson

| § | Section | Key ideas |
| :--- | :--- | :--- |
| 1 | Ways to lose data | A wrong `delete` or `update`; a bad migration; a deleted project; a lost machine; an agent run against the wrong database |
| 2 | Logical backups | `pg_dump --format=custom`, `--schema`, `--table`, `--data-only`; `pg_restore --list`, `--table`, `--clean`; a backup file contains everything a reader of the table could see |
| 3 | Two numbers | Data-loss window (time between the last good backup and the failure) and restore time (failure to service). Measure them, do not guess |
| 4 | Restoring is the test | A backup that was never restored is a hope. Restore into a different place first; compare counts; then copy rows back |
| 5 | Replicas | A second server that replays the first one's changes within a second; good for a dead server and for read load; useless against a wrong statement |
| 6 | Point in time | Keeping the change log lets you stop the replay just before the mistake (named only; the free plan does not include it) |
| 7 | Keeping backups safe | Not in the repository (`backups/` ignored); encrypted at rest; who can read them; how long they are kept |
| 8 | In GPIS | "This project has already lost a test database to an agent-run process." Backups are encrypted and restores are tested |

- **Diagram (text):** a timeline: backup 08:00 — writes — wrong delete 10:40 — noticed 10:55 — restored 11:20; with "data-loss window" and "restore time" marked; under it a replica line that copies the delete at 10:40:01.
- **Common mistakes**
  1. "We have a replica, so we have a backup" → the delete is on both → backups are separate copies in time.
  2. Restoring straight over the live table → you destroy the evidence and the newer good rows → restore beside, compare, copy.
  3. Committing a dump file → every student's data is in Git for ever → ignore `backups/`.
  4. Never timing the restore → the first real one takes four times as long → practise and write the time down.
  5. Backing up without `--no-owner` / role notes → the restore fails on another server → read the restore's errors once, in practice.

### Guided example — "Lose one table, get it back" (first half in full)

Schema `example_recovery` in the lab database, table `notes` with 20 rows.

1. `pg_dump "$LAB_DATABASE_URL" --schema=example_recovery --format=custom --file=backups/example.dump`; `ls -lh`; `pg_restore --list`. *(full)*
2. Confirm `backups/` is ignored by Git. *(full)*
3. `delete from example_recovery.notes where id > 5`; count. Note the time. *(full)*
4. Restore into a **new** schema (dump with `--schema`, restore after `alter schema … rename` — the page gives the exact sequence); compare counts in both. *(full)*
5. Now copy back only the missing rows with `insert … select … where not exists`. *(task)*
6. Now add 3 new rows **after** the backup and before the delete, repeat, and say which rows cannot come back and why. *(task)*
7. Now write the two numbers for this drill. *(task)*

### Quiz plan (`m4-u6-quiz`, 6 questions, pass mark 4)

| # | Idea | Right answer | Wrong options and why |
| :--- | :--- | :--- | :--- |
| 1 | A wrong `delete` runs on the primary. One second later the replica has | The same rows deleted | The old rows, safe (it replays every change); a warning; a copy from an hour ago |
| 2 | Backup at 08:00, wrong delete at 10:40, restored from the 08:00 backup. What is lost for good? | Changes made between 08:00 and 10:40 that are not in the backup | Nothing; only the deleted rows; everything since yesterday |
| 3 | "Restore time" means | The time from the failure until the service works again | How long `pg_dump` takes; how old the backup is; how long the backup is kept |
| 4 | Find the mistake: `git add backups/term1.dump` | A dump holds every student's data; it must never be committed | "Dumps are too large for Git" (true sometimes, not the reason); "It needs compressing first"; "Nothing is wrong" |
| 5 | Safest first step when restoring one damaged table? | Restore the backup beside the live table and compare | Drop the live table and restore over it; restore the whole database over the live one; re-run all migrations |
| 6 | Why practise a restore when backups run every night? | Only a restore proves the backup is usable and tells you how long it takes | To use up free quota; because backups expire after one use; it is not needed |

### Debugging lab — "The backup that was empty"

| Item | Design |
| :--- | :--- |
| Seeded | A script `nightly.sh` (printed) and three "backup files" it produced, made by a setup script in `~/academy-labs/scratch/u4-6/`: sizes 48 KB, 48 KB, 0 KB; a log `nightly.log` |
| Symptom | "The nightly backup has reported 'backup ok' for a month. Today we needed it and the newest file is empty." Then: "The older file restores, but the students table has 0 rows." |
| Fault 1 | `pg_dump … > file; echo "backup ok"`: no `set -e`, and when the password expired `pg_dump` failed, leaving an empty file and a cheerful log |
| Fault 2 | The dump uses `--schema-only` (a flag left from a test), so no backup ever held data |
| Evidence | Observe: `ls -l`, the log, `pg_restore --list` of an older file (no `TABLE DATA` entries). Causes: disk full; dump failed; wrong flags. Tests: run the script with a wrong URL and read `$?`; search the list for `TABLE DATA`. Fix 1: `set -euo pipefail`, write to a temporary name and rename on success, check the size. Fix 2: remove the flag. Add: a monthly restore test is the only thing that would have caught fault 2 |
| Fixed state | The script exits non-zero and leaves no file when the dump fails; a good run's file lists `TABLE DATA`; `diagnosis.md` says how long the fault went unnoticed and why |
